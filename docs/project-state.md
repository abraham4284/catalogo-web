# Estado vigente

Current phase: F17 completed.

- Frontend: React + TypeScript + Vite Storefront; shell público compartido con StoreLayout, Header y Footer VITRUNO y responsive.
- Routing: `/`, `/productos`, `/productos/:slug`, `/carrito`, `/contacto`, `/como-comprar`, `/preguntas-frecuentes` y `*` dentro del layout; detalle consume API real, Not Found con regreso al inicio. Slugs de producto inválidos no montan fetching ni hacen requests. Header recibe unidades y total desde StoreRoute → StoreLayout; shared no importa Cart.
- Environment: `config/env.ts` valida de forma lazy VITE_CATALOG_API_URL (prefijo completo /api/public) y VITE_WHATSAPP_NUMBER (público, solo 8–15 dígitos internacionales, sin default). `.env.example` documenta ambas; configuraciones locales ignoradas. Build funciona sin datos reales configurados.
- Backend: backend comercial Cajora desplegado separadamente.
- Catalog API: frontera para negocio, categorías, listado y detalle, con Zod y tipos derivados. Contrato F10A: slugs públicos de producto/categoría, saleMode, availabilityStatus y availabilityNote nullable; sin available en Catalog. stockAvailable entero no negativo del depósito principal/default activo; listado con secondaryImageUrl nullable, detalle con gallery y richContent nullable v1 (sin requerir secundaria). Sin endpoints administrativos ni requests de detalle por card. Se conservan reglas de paginación, errores/cancelación y totalPages >= 1/sortOrder >= 0.
- Catalog UI: Home sigue consultando negocio/categorías/primeros 8 productos; catálogo consulta 24 por página con filtros URL. ProductCard única con descripción corta (clamp CSS), enlace informativo único y acciones rápidas externas. La secundaria se monta al primer pointerenter mouse/pen; touch conserva la portada y reduced-motion elimina la transición. ProductGrid ofrece renderActions; app/compositions integra agregar y consulta individual para ambas páginas. Disponibilidad comercial usa exclusivamente availabilityStatus: Disponible/No disponible/Por encargo; solo in_stock ofrece agregar y ON_ORDER no agrega incluso con stock físico; nunca se muestra stock exacto. Grid prioriza una columna en anchos pequeños, dos desde 540 px, tres md y cuatro xl.
- Product detail: descripción opcional como introducción, acciones de agregado/consulta y rich content bajo el bloque galería/datos. RichContentRenderer genera headings h2/h3, párrafos, listas y specs dl a partir del schema v1; sin HTML arbitrario. Galería conserva portada/orden/deduplicación y miniaturas accesibles: columna lateral en desktop y tira horizontal en mobile. Breadcrumbs usan categoría por slug; panel comercial y nota reciben los tokens VITRUNO. ProductImage compartido con carrito para fallback. Fetching abortable; cambio de slug reinicia contenido; 404 presenta copy neutral sin inferir motivo ni usar texto backend. availabilityNote no vacía se muestra como texto plano en cualquier estado. Límites de rich content alineados al contrato definitivo.
- Catalog filters: search/categoria/page en URL; categoria lleva slug y API recibe categorySlug, parsing seguro de parámetros inválidos; cambio de búsqueda/categoría reinicia página y paginación conserva filtros. Página superior a totalPages redirige a la última válida con replace, conservando filtros. Requests abortables con protección de respuestas obsoletas.
- Database: DB_COMERCIO independiente de Cajora SaaS DB.
- Brand: VITRUNO, logo propuesta 3 y dirección Tech contemporánea (DEC-011): #FAFAFC fondo, #242038 foreground/shell oscuro, #6547BE primary, #EAE6F7 accent/secondary y cards blancas. Paleta anterior superada (historia DEC-010/F12). Manrope/Inter conservadas. PNG opacos locales íntegros; horizontal corregido 1200×630 desktop/Footer e isotipo accesible centrado en Header mobile. Footer mobile centra logo, nota y navegación; desktop conserva izquierda/derecha. business.name/logoUrl permanecen en contrato/hook, sin representar la marca pública.
- Cart: Zustand + localStorage v3, clave catalogo-web-cart. Snapshot idProduct/slug/name/price/imageUrl/availabilityStatus/stockAvailable y quantity; sin booleano legacy ni campos comerciales ajenos. v1/v2/futuras, JSON corrupto, IDs/slugs duplicados y campos inválidos producen vacío seguro; storage bloqueado/lleno conserva memoria usable. Solo in_stock con stock >= 1 agrega, incrementa hasta el último stock conocido y decrementa con mínimo 1. Re-agregar actualiza snapshot; reconcile preserva quantity y evita writes idénticos. Imagen/nombre forman un único enlace /productos/<slug>. Agotado/encargo permanecen visibles con cantidad deshabilitada; exceso de quantity mantiene aviso, permite disminuir/eliminar y bloquea checkout.
- Cart snapshot: Revalidación coordinada en app/compositions: al montar /carrito con items, cambiar el conjunto idProduct+slug o reintentar. Una request concurrente por item a getCatalogProductBySlug, sin Axios en páginas ni acoplar Cart a Catalog. Verifica ID/slug de respuesta; identidad distinta, nombre vacío, 404 ambiguo, red/error HTTP o contrato inválido conservan snapshot y marcan fallo. Éxitos parciales actualizan precio/nombre/imagen/status/stock. AbortController y comprobación del conjunto actual impiden reconciliar corridas obsoletas. Quantity, reconcile y renders no disparan requests. Estado runtime loading/success/error con failedProductIds y retry, sin persistencia.
- Checkout: CTA de carrito “Finalizar compra por WhatsApp”, solo con verificación success y carrito coherente in_stock; loading/error/inconsistencia bloquean. Retry visible ante error; precio actualizado llega al mensaje. Sin stock/status/slug/IDs en mensaje, sin envío automático ni limpieza automática del carrito.
